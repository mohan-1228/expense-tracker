# Pennyroom — Engineering & Architecture Report

A reference doc for talking about this app: what it does, the full tech stack and why each piece was chosen, every AWS service in use and how it's wired together, the real engineering decisions (and the bugs that forced them), and a prep set of interview questions an AWS interviewer would plausibly ask about a project like this.

Live app: **https://pennyroom.thapa.dev**

---

## 1. What this app does

Pennyroom is a personal + shared expense tracker:

- Personal expense tracking with categories, a monthly calendar heatmap, and category breakdowns.
- **Group expenses** — split a cost evenly among a group, track who owes whom, settle up.
- **Recurring expenses** — rent, subscriptions, etc. auto-generate on schedule via a daily cron job.
- **AI weekly summary** — a "this week in review" card, generated by Amazon Bedrock, cached per user per week.
- **Penny** — an AI chatbot that answers free-form questions about your own spending ("how much did I spend on food this month?", "who owes me money?"), grounded in real database queries via tool calling, not guesses.
- Deployed for real: custom domain, HTTPS, containerized backend, managed Postgres — not just running on `localhost`.

---

## 2. Architecture at a glance

```
Browser
  │  HTTPS (pennyroom.thapa.dev)
  ▼
CloudFront ──default behavior──▶ S3 (private, OAC-only) ──▶ React SPA build
  │
  └──/api/* behavior──▶ EC2 (Docker container: Node/Express)
                            │
                            ├──▶ RDS PostgreSQL (private subnet, SG-restricted)
                            └──▶ Amazon Bedrock (Claude Haiku 4.5, via inference profile)
```

One domain, one TLS certificate, two origins. The frontend and API are same-origin from the browser's point of view, which is a deliberate choice explained in §6.

## 4. AWS services — what, how, and why

This is the part worth knowing cold. Each service below includes the actual configuration used, the reasoning, and a real problem hit while building it — these war stories are better interview material than a clean, idealized description would be.

### Amazon EC2

- **Role:** hosts the Dockerized Express backend.
- **Config:** `t3.micro`, Ubuntu 26.04, public subnet, an Elastic IP attached, Docker installed via the official convenience script.
- **Why:** full control over the runtime for a small, single-service app, at the lowest cost that avoids paying for a managed orchestrator (ECS/Fargate) that wasn't needed yet.
- **Real-world relevance:** EC2 fundamentals — AMIs, security groups, key pairs, Elastic IPs — are the baseline AWS compute knowledge almost every AWS interview probes, even when the "real" target architecture is containers or serverless.
- **War story:** the instance's public IP changed every time it stopped and restarted, silently breaking SSH access and anything that had bookmarked the old address. Fixed permanently with an Elastic IP — a fixed address that survives stop/start.

### Amazon RDS (PostgreSQL)

- **Role:** managed, private relational database.
- **Config:** `db.t3.micro`, 20 GB storage, private subnet, `PubliclyAccessible: false`. Its security group accepts port 5432 **only from the EC2 security group** — not from any IP address, not even mine.
- **Why:** managed backups, patching, and failover instead of self-managing Postgres on a box; security-group-to-security-group referencing (instead of IP allowlisting) is the correct, standard way to protect a database tier.
- **Real-world relevance:** "how do you secure a database in AWS" is a near-guaranteed interview question. The concrete, defensible answer here: private subnet + SG-to-SG reference, not an IP allowlist (which breaks the moment an IP changes, and doesn't scale to multiple app servers anyway).
- **War story:** connecting required a real TLS handshake using AWS's CA bundle (`global-bundle.pem`). The original `.env` pointed at a host-filesystem-absolute path for that cert, which didn't exist inside the Docker container — had to be rewritten to the container's own path before the backend could connect at all.

### Amazon S3

- **Role:** stores the built React SPA (static HTML/CSS/JS).
- **Config:** bucket is fully private (all public access blocked), readable only via CloudFront's **Origin Access Control (OAC)**, with a bucket policy scoped to one specific CloudFront distribution ARN — not "any CloudFront distribution," and not public at all.
- **Why:** S3 is the standard way to host a SPA build — cheap, durable, effectively infinite scale, and purpose-built to pair with CloudFront.
- **Real-world relevance:** "static site on S3 + CloudFront" is one of the most common real AWS architectures (marketing sites, docs, SPAs) and a frequent system-design interview prompt.

### Amazon CloudFront

- **Role:** the single public entry point — HTTPS termination, CDN caching for the frontend, and path-based routing of `/api/*` to the EC2 backend.
- **Config:** two origins (S3 via OAC; EC2 via its public DNS hostname, since custom origins can't be a bare IP). Two cache behaviors: the default (`CachingOptimized` → S3) and `/api/*` (`CachingDisabled` + the `AllViewer` origin request policy + all HTTP methods → EC2). Custom error responses map 403/404 to `/index.html` with a `200` status, so refreshing a client-side route like `/dashboard` doesn't break.
- **Why:** putting the frontend and the API behind the same domain eliminates CORS entirely (the browser sees one origin) and gives the API free HTTPS — no separate certificate or load balancer needed just for the backend.
- **Real-world relevance:** using a CDN as the unifying edge layer in front of heterogeneous origins (static storage + a dynamic API) is a genuine production pattern, not a toy-project shortcut.
- **War story 1:** CloudFront custom origins must be a DNS name, never a bare IP. The EC2 instance had no public DNS hostname at all — traced to the VPC's `enableDnsHostnames` attribute being disabled. Enabling it produced the auto-generated `ec2-x-x-x-x.compute-1.amazonaws.com` hostname needed as the origin.
- **War story 2:** after wiring `/api/*` to EC2, every request 504'd. The security group only allowed *my own laptop's* IP on port 5001 — but CloudFront connects from AWS's own edge IP ranges, not mine. Fixed correctly with AWS's **managed prefix list** for CloudFront (`pl-3b927c52`), not by opening the port to the whole internet.

### Amazon Route 53

- **Role:** DNS for `thapa.dev`; hosts the `pennyroom.thapa.dev` alias record and the ACM validation record.
- **Why:** already the DNS host for the domain. An **ALIAS** record (AWS-specific, free) points the subdomain at the CloudFront distribution — a plain CNAME has restrictions a regular ALIAS doesn't.
- **Real-world relevance:** DNS fundamentals — A vs. CNAME vs. ALIAS, TTLs, validation records — come up constantly in "how would you set this up" interview questions.
- **War story:** discovered mid-project that the *portfolio* site's own CloudFront distribution lives in a **completely different AWS account** than this project — only the Route 53 zone itself was visible/shared. That's the actual reason this app got its own subdomain instead of a path on the main site: not just the cleaner option, but the only one actually possible with the access available.

### AWS Certificate Manager (ACM)

- **Role:** issues and auto-renews the TLS certificate for `pennyroom.thapa.dev`.
- **Config:** DNS validation (not email), validation CNAME added to Route 53, certificate attached directly to the CloudFront distribution.
- **Why:** free, auto-renewing HTTPS, zero manual certificate management — the standard pairing with CloudFront.
- **Real-world relevance:** knowing *why* ACM certificates used by CloudFront must be requested in `us-east-1` regardless of where everything else lives is a specific, testable detail interviewers like to probe.

### IAM

- **Role:** controls who/what can call AWS APIs. Right now that's the CLI user `mohan-cli`, used for all provisioning in this project.
- **Current state, stated honestly:** `mohan-cli` has `AdministratorAccess`. That's acceptable for solo learning/dev, and explicitly **not** least-privilege. The intended next step (not yet done) is a scoped role limited to exactly `bedrock:InvokeModel` on one specific model ARN for whatever actually calls Bedrock in production.
- **Real-world relevance:** least privilege is probably the single most-tested AWS security concept in interviews. A real, specific example of where it *hasn't* been applied yet — and a clear explanation of why that's wrong and what the fix looks like — is more credible than claiming everything is already perfect.

### Amazon Bedrock

- **Role:** powers two AI features — the weekly spending summary and the Penny chatbot — both through the **Converse API** using a small, cheap Claude model.
- **Config:** model `anthropic.claude-haiku-4-5-20251001-v1:0`, actually invoked via the **inference profile** `us.anthropic.claude-haiku-4-5-20251001-v1:0`. The bare model ID failed outright with "on-demand throughput isn't supported" — some newer Bedrock models require routing through a regional inference profile rather than the base model ID.
- **Why Bedrock over calling an LLM provider directly:** credentials and billing stay inside AWS IAM — no separate API key to issue, rotate, or leak — and it integrates naturally with the rest of the AWS-native stack.
- **The design principle worth repeating in an interview:** *the database does the arithmetic; the model only writes the sentences.* Every number the AI ever mentions is computed by SQL first. The prompt explicitly forbids the model from calculating anything itself.
  - **Weekly summary:** a SQL-computed "facts" JSON (this week vs. last week totals, category breakdown, top expenses, net group balances) is handed to Claude with instructions to write 3–4 plain-English sentences from *only* those numbers. Cached per user per week in a `weekly_summaries` table, so it's not regenerated (and re-billed) on every page load — with a template-based fallback if the Bedrock call itself fails, so a flaky AI call never breaks the dashboard.
  - **Penny chatbot:** real **tool use / function calling**. Claude is given four tools (`get_spending_summary`, `list_expenses`, `get_balances`, `get_recurring_expenses`), decides which one(s) a question needs, the backend runs the actual SQL, and only the real results go back to the model to answer from. This is the same grounding pattern used in production AI agents everywhere — the standard way to stop an LLM from inventing numbers.
- **Real-world relevance:** Bedrock plus tool use maps directly onto current "AI engineer" and "ML platform" roles. Being able to explain *why* a cache and a fallback exist — not just that an LLM was "called" — is what separates a real answer from a buzzword.

### Networking primitives (VPC, security groups, Elastic IP)

- A dedicated VPC houses EC2 (public subnet) and RDS (private subnet).
- Two security groups: one for EC2 (SSH + API port from a specific IP, plus the API port from CloudFront's managed prefix list), one for RDS (Postgres port, source = the EC2 security group, not a CIDR range).
- An Elastic IP gives EC2 a fixed address so DNS, CloudFront, and bookmarks don't break on every restart.
- **Real-world relevance:** this is the actual shape of "simple but correctly secured" AWS networking — the kind of setup a junior-to-mid engineer is expected to both build and explain clearly.

## 5. Database schema

| Table | Purpose |
|---|---|
| `users` | Accounts — email, bcrypt password hash, name |
| `categories` | Default (shared) + per-user custom expense categories |
| `groups` | Named groups for shared expenses |
| `group_members` | Many-to-many: which users belong to which groups |
| `expenses` | Every expense — personal (`group_id IS NULL`) or group-owned, who paid, amount, date, category |
| `expense_shares` | One row per member per group expense — their portion, and whether it's settled |
| `recurring_templates` | Recurring expense definitions (amount, frequency, next occurrence); a daily cron job turns due ones into real `expenses` rows |
| `weekly_summaries` | Cached AI-generated (or fallback) weekly summary text per user per week, plus the facts JSON it was built from |

The one detail worth highlighting: a single query resolves "what did *this specific user* actually pay," uniformly for personal and group expenses — the full amount for personal ones, their individual share for group ones. Every feature that aggregates spending (the dashboard, the weekly summary, Penny's tools) reuses that same resolution logic instead of each reimplementing it slightly differently.

## 6. Security posture, summarized

- Passwords: bcrypt-hashed, never logged or stored in plaintext.
- Auth: JWT, verified per request, no server-side session state.
- Database: private subnet, no public accessibility, security-group-to-security-group access only.
- S3: fully private; only CloudFront (via OAC, scoped to one distribution ARN) can read it.
- Network access to the backend: locked to a specific IP (admin) and CloudFront's managed prefix list (public traffic) — never opened to `0.0.0.0/0`.
- Secrets: real credentials live only in gitignored `.env` files on the EC2 instance and locally — never committed, never in the Docker image (excluded via `.dockerignore`).
- Same-origin architecture (via CloudFront) removes an entire class of CORS misconfiguration risk.

## 7. What's genuinely missing (said honestly)

A good engineer can name these without being asked twice:

- **No automated tests.** Everything in this project was verified by hand (curl, real signups, real data) during development — thorough, but not repeatable or regression-proof.
- **No CI/CD.** Deploys are a manual `git pull` + `docker compose up -d --build` over SSH. No pipeline, no automated rollback.
- **No monitoring/alerting.** No CloudWatch alarms, no centralized logs, no uptime checks. If the container crashes at 3am, nothing notices automatically.
- **Single point of failure.** One EC2 instance, no load balancer, no auto-scaling, single-AZ RDS. Fine for personal use; not how you'd run this for real traffic.
- **IAM is not least-privilege yet.** `AdministratorAccess` on the working CLI user, not a scoped role.
- **No WAF.** CloudFront has no AWS WAF rules in front of it — no rate limiting or bot/exploit filtering beyond what CloudFront does by default.
- **node-cron runs in-process.** Fine at one instance; would double-fire recurring expenses if scaled to two app servers without change.

## 8. Interview prep — likely questions about this app

Grouped by topic, with the actual, specific answer this project supports — not a generic textbook answer.

### Networking & security

**Q: Why isn't your RDS instance publicly accessible, and how did you restrict access to it?**
It sits in a private subnet with `PubliclyAccessible: false`. Its security group allows Postgres traffic only from the EC2 security group — a security-group reference, not an IP range. That means only things running with that specific security group can ever reach the database, regardless of what IP they're on.

**Q: Why reference a managed prefix list instead of just allowing 0.0.0.0/0 for your API port?**
Because CloudFront doesn't connect from a fixed IP — it connects from AWS's edge network, which spans many IP ranges that also change over time. AWS publishes and maintains a managed prefix list (`pl-3b927c52`) specifically for this, so the security group rule tracks CloudFront's real IP ranges automatically instead of either going stale or being opened to the entire internet.

**Q: How does your frontend avoid CORS issues despite calling a separate backend?**
It doesn't call a "separate" backend from the browser's perspective — CloudFront serves both the SPA and `/api/*` from the same domain. Same origin, so the browser never triggers a CORS preflight at all. (The backend's CORS config is still there, configurable via an env var, as a fallback for direct access outside CloudFront.)

**Q: Your EC2 instance's IP kept changing — why, and how did you fix it?**
EC2 assigns a new public IP by default every time an instance stops and starts. An Elastic IP is a static IP you allocate and associate with the instance — it survives restarts, so DNS, CloudFront's origin config, and SSH access all stay valid.

### Compute, containers & deployment

**Q: Why EC2 + Docker instead of a serverless option like Lambda or Fargate?**
For a single long-running Express server with a persistent node-cron job, EC2 is simpler and cheaper at this scale than paying for a managed container orchestrator. Docker still gets the main benefit — a portable, reproducible build — without the added complexity of ECS task definitions, service discovery, etc., which would be the right call if this needed to scale horizontally.

**Q: Walk me through your Dockerfile. Why copy `package.json` before the rest of the source?**
Docker caches each instruction as a layer. Copying `package*.json` and running `npm ci` *before* copying the rest of the source means that layer only gets invalidated when dependencies actually change — not on every code change — so rebuilds reuse the cached `npm ci` layer and are much faster.

**Q: What would you change to make this horizontally scalable?**
Move the backend behind an Application Load Balancer with multiple EC2 instances (or ECS/Fargate tasks) instead of one box; move the cron job out of the app process into EventBridge Scheduler + a dedicated job (or add distributed locking) so it doesn't fire once per instance; and move RDS to Multi-AZ for failover.

**Q: What's the actual deploy process today, and what's wrong with it?**
SSH in, `git pull`, rebuild and restart the container. It works, but it's manual, has no rollback path, and nothing validates the build before it replaces the running one. A real pipeline (GitHub Actions building and pushing an image, then triggering a deploy) is the obvious next step.

### Database

**Q: Why Postgres over something like DynamoDB here?**
The data is relational by nature — a user belongs to groups, a group expense has multiple shares referencing both the expense and each user, balances have to be computed by joining across those relationships with real consistency guarantees. That's exactly the shape relational databases and SQL joins are built for; forcing it into a NoSQL key-value model would mean re-implementing joins and consistency in application code.

**Q: How do you manage schema changes?**
Every change is a numbered, reversible migration file (`node-pg-migrate`), run the same way in every environment. No one hand-edits the schema directly in any environment.

**Q: What would you change for RDS at real scale?**
Multi-AZ for automatic failover, a read replica if read traffic grew disproportionately, and connection pooling (e.g., RDS Proxy or PgBouncer) once there are enough concurrent app instances that direct connections become the bottleneck.

### CDN / frontend delivery

**Q: Why CloudFront in front of S3 instead of serving straight from S3?**
HTTPS (S3 website hosting alone doesn't give you a custom-domain TLS certificate), edge caching for latency, and — specific to this app — the ability to also route `/api/*` to a completely different origin from the exact same domain.

**Q: How does a hard refresh on `/dashboard` work, given there's no server-side route for it?**
CloudFront's custom error responses map both 403 and 404 to `/index.html` with a `200` status. S3 returns one of those for any path that isn't a real object (like `/dashboard`), CloudFront rewrites it to serve `index.html` instead, and React Router takes over from there once the JS loads.

**Q: Why do cache invalidations matter, and why aren't they free at scale?**
Without invalidating, CloudFront keeps serving the old cached build after a deploy — clients could see stale JS/CSS for the length of the cache TTL. AWS gives a limited number of free invalidation paths per month; past that, each one is billed, so at scale you'd rely more on cache-busting via content-hashed filenames (which Vite already does) and invalidate far less often.

### AI / Bedrock

**Q: Why Bedrock instead of calling an LLM API directly?**
Credentials and billing stay inside AWS IAM — no separate API key to manage or rotate — and it composes naturally with the rest of an AWS-native stack (same SDK credential chain as everything else).

**Q: What's an inference profile, and why did you need one?**
Some newer Bedrock models can't be invoked by their base model ID under on-demand throughput — AWS requires routing the request through a regional "inference profile" ID instead. Found this out directly from a `ValidationException` the first time the model was actually called; the fix was using `us.anthropic.claude-haiku-4-5-20251001-v1:0` instead of the bare model ID.

**Q: How do you keep the AI from making up numbers?**
The model never sees raw data without structure, and it's never asked to do arithmetic. For the weekly summary, the backend computes every figure in SQL first and hands the model a small JSON of already-correct numbers with instructions to only phrase them as sentences. For Penny, the model doesn't have database access at all — it can only request one of four defined tools, the backend executes the actual query, and the real result is what gets sent back for the model to answer from.

**Q: Explain the tool-use pattern in Penny.**
Four tools are defined with JSON schemas (spending summary, expense list, balances, recurring expenses). On each turn, Claude either returns a final answer or requests a tool call with structured arguments; the backend executes that exact function against Postgres and returns the real result as a new message; this can repeat (capped at 5 rounds to bound cost) until the model has enough real data to answer the original question.

**Q: How do you control Bedrock cost?**
A small, cheap model (Claude Haiku), a hard cap on output tokens per call, a cap on tool-call rounds per chat turn, and caching the weekly summary so it's generated once per user per week instead of on every dashboard load.

### Cost & operations

**Q: What does this cost per month?**
EC2 `t3.micro` (~$0.0104/hr if always on), RDS `db.t3.micro` + 20 GB storage, S3 storage (negligible for a SPA build), CloudFront requests/data transfer (also small at low traffic), Route 53 hosted zone (~$0.50/month), and Bedrock billed per token on a cheap model with caching to minimize call volume. The two real levers are EC2+RDS uptime (stop them when not in use) and Bedrock call frequency (the caching already handles most of this).

**Q: What's missing before you'd call this production-ready?**
Automated tests, a real CI/CD pipeline, monitoring/alerting, a scaled-down IAM role instead of admin access, and redundancy (load balancer + multiple instances, Multi-AZ RDS) — all listed explicitly in §7, because naming your own gaps accurately is itself a signal.
